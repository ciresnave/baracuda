## Ideas swept
Mechanisms baracuda implements itself (third-party code it vendors, such as FlashAttention-2, Marlin / AWQ and the llama.cpp GGUF kernels, is outside this list and keeps its upstream licences; it is not swept here).

1. Emitting CUDA C++ from a neutral scalar-expression IR where each node carries an explicit numeric qualifier (rounding mode, flush-to-zero, approximate) spelled as a distinct hardware intrinsic, and the emitter declines with a typed refusal rather than dropping a qualifier it cannot spell.
2. Verifying generated GPU kernels by running them on the device and comparing bit for bit against an independent CPU interpreter of the same IR, over an edge-value table and every rounding mode.
3. Float-to-integer conversion emission with an explicit NaN-to-zero guard on the 64-bit and double-source paths, because the intrinsics return the type minimum for NaN (found by the oracle comparison).
4. Lazy per-symbol dynamic loading of vendor GPU libraries with per-platform, per-version candidate file names and typed errors when a library or symbol is absent.
5. A C++ shim giving a flat C ABI over a C++-only vendor API (TensorRT) by pure virtual-table dispatch on pointers created through the library's exported `extern "C"` factory, so the shim references no vendor symbol at link time.
6. One process-wide logger object registered with a vendor library that accepts only one logger, fanning each message out to the logger handles currently alive.
7. Deterministic backward pass of reflect / replicate / circular padding as an output-indexed gather in fixed order with an f32 accumulator for half types, instead of atomic scatter.
8. A block-wide GPU reduction that reads its result into a register before the second barrier, avoiding a shared-memory race between consecutive reductions.
9. An ABI manifest of per-symbol signature hashes checked in CI against the generated C header.
10. Capability gating that separates a data type's storage support from its arithmetic support per GPU architecture.
11. Rust lifetimes tying vendor builder-API objects (tensors, layers, optimization profiles) to the network or builder that owns them, with constant weights kept alive by the network until the build.
12. A machine-wide advisory GPU lock plus a test harness in which a test that cannot run must declare a skip with a reason, and the runner reports declared skips and the ran count.
13. Emitting packed `__half2` / `__nv_bfloat162` paired operations from a scalar elementwise IR when the body is packable, scalar otherwise.
14. Per-context run-time selection of an optimization profile (asynchronously, on a stream) for a dynamic-shape inference engine built from a network with min / opt / max shapes validated at build time.

## Claim charts (added 2026-10-25 on the PM's request, board 296(E))
Claims below were read in full with `C:\Projects\tools\patent-claims.py` (Google Patents text; status and expiry are Google's estimates, not the official record). A claim reads on a product only if EVERY element is present; absent elements are listed first. This is a literal-reading chart; the doctrine of equivalents is a question for counsel.

### US 8,458,680 B2 (Google, active, est. expiry 2030-08-08), claim 1 (claims 9 and 17 repeat it as system and medium)
**Absent elements (each alone defeats a literal reading):**
- "a parallel-processing computer that includes **multiple types of processing elements using shared memory**" and "**choosing a respective type of processing element** ... selected from the group consisting of ... central processing units, graphics processing units and ... co-processors" at run time. baracuda dispatches to NVIDIA GPUs only; it has no CPU / GPU / co-processor selection. The nearest thing is a choice between two GPU kernel implementations, which is not a choice among processing-element types: `crates/baracuda-kernels/src/gemm/int_gemm.rs:55-58` (`Backend::Cutlass` vs `Backend::Bespoke`, both GPU), `attention/flash_sdpa.rs:94` and `flash_sdpa_backward.rs:75` (`BackendChoice`, both GPU), `baracuda-cutlass/src/plan.rs:3313`.
- "**at a runtime system** ... receiving one or more operation requests issued by an application" as a scheduler. baracuda is a library the application calls; each `Plan::run` is a direct call, and there is no runtime system that receives requests and schedules them.

**Present (in substance):**
- "identifying, from a library, a precompiled, processor-specific compute kernel corresponding to the intrinsic operation or the primitive operation": the kernel library is `baracuda-kernels-sys`, and a plan picks the precompiled kernel by dtype, e.g. `crates/baracuda-kernels/src/shape_layout/repeat.rs:206-229` (`dispatch!(baracuda_kernels_repeat_f16_run)` per `ElementKind`).
- "preparing one or more compute kernels ... configured to execute on the respective type of processing element": the plan's launch of the chosen symbol on a CUDA stream (same file).

**Reading:** two elements are absent. Verdict: `design-around` (we do not choose a processor type at run time; GPU-only by design). Keep it that way: a future CPU fallback or CPU / GPU auto-selection in baracuda itself would need counsel review first.

### US 8,146,066 B2 (Google, active, est. expiry 2030-07-05), claim 1 (claims 8 and 15 repeat it)
**Absent:** "**dynamically choosing a respective type of processing element** for the intermediate representation entries" among CPUs, GPUs and co-processors (as above); "**generating one or more intermediate representation entries** for the operation requests" by the runtime system at run time for "a code reuse section of the application"; "scheduling execution ... at the respective type of processing element". baracuda has no run-time IR generation for application operation requests; the IR lives in `unpopped`, and the emitter runs ahead of time or in an explicit user-invoked JIT (`crates/baracuda-cuda-emit/src/nvrtc.rs`, feature `nvrtc`), which targets one GPU.
**Present in part:** "identifying, among a plurality of compute kernels previously compiled ... one or more previously compiled compute kernels": precompiled kernels are selected by symbol; but they were compiled at build time, not "previously compiled by the runtime system for the application".
**Verdict:** `design-around` (three elements absent).

### US 8,584,106 B2 (Google, active, est. expiry 2030-07-05), claim 1 (claims 5, 10, 14, 18, 22 are variants)
**Absent:** "first and second processing elements, each having a **different instruction set architecture**" executing the kernel set (baracuda runs one GPU ISA per launch); "at run-time, while the application is executing ... **compiling** one or more compute kernels for a first portion of the intermediate representation **for execution on the first processing element**" together with "**searching a set of previously compiled compute kernels**" for a second portion and "**executing the set ... on the first and second processing elements**". The only run-time compile is the opt-in NVRTC path (`nvrtc.rs`), which compiles for one GPU target and has no kernel-cache lookup (`grep -i -c cache crates/baracuda-cuda-emit/src/nvrtc.rs`: 0; positive control: `grep -i -c compile` on the same file: 32).
**Verdict:** `design-around`.

### US 8,261,270 B2 (Google, active, est. expiry 2030-08-31), claim 1 (claims 9 and 17 repeat it)
Elements: a runtime system that at run time receives a plurality of operation requests from an application and automatically (a) selects a subset to run on a **target** processing element, (b) prepares kernels for a **reference** processing element of a different type and runs them to get a reference result, (c) prepares and runs kernels on the target element for a target result, (d) compares the two, and (e) "**based on the result comparison exceeding a predefined non-zero value**, aborting execution of the application or storing a result mismatch signal in a log file".
**Absent:** the run-time-system framing (a subset of an application's operation requests chosen automatically while it runs); a **predefined non-zero** threshold (ours is a bit-for-bit comparison, zero tolerance); abort-the-application or mismatch-log behaviour (ours is a failing test).
**Present in part:** the structure of `crates/baracuda-cuda-emit/tests/typed_exprs.rs` (generated CUDA kernel on the GPU vs the CPU oracle `unpopped::oracle::evaluate`, lines 4-6, 15-19, 197-243) mirrors (b) and (c) for a fixed table of test inputs. It is a developer test that the user runs, not a run-time system acting on an application's requests.
**Verdict:** `design-around` leaning clear. The oracle-comparison idea is the closest in spirit to any claim here, so a lawyer should read claim 1 against the test harness once.

### US 2024/0103872 A1 (Intel, pending), claim 1
Claim 1 is an apparatus with **decoder circuitry** decoding a single instruction whose opcode converts floating-point elements to integers with truncation and saturation; claims 8 and 15 are a method of translating that instruction and a system. All independent claims recite instruction decode and execution circuitry. baracuda emits CUDA source (`crates/baracuda-cuda-emit/src/typed.rs`) and implements no instruction decoder. **Verdict:** clear (hardware instruction claims). It is pending, so re-check if it is granted with amended claims.

### US 8,806,458 B2 (Microsoft, active, est. expiry 2032-10-13), claim 1
Claim 1 is "vectorizing an input shader ... using a central processing unit (CPU) with a vector width W, wherein the CPU is not a graphics processing unit", with input intermediate language code "comprising divergent flow control and N elements, where N is greater than W", scope annotations as predicated / non-predicated and scope masks, and output code "executed by the CPU". Claims 9 and 16 are the same on a CPU. **Absent:** CPU execution, shader-language input, divergent control flow and scope masks, each alone. baracuda emits `__half2` CUDA for a GPU from straight-line elementwise bodies. **Verdict:** clear. The earlier "a human should confirm" is resolved by reading the full claims.
